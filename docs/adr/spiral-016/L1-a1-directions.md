> 人類的決定：完整版：穩定訊息身分 + 歷史協定 + 向上捲動載入

## 現在是什麼狀況

在手機上打開一個 session，聊天區是空的，要等下一輪對話才有東西。這不是 bug：讀回機制刻意把游標放在 transcript 檔尾（`server/transcript/delivery.ts:117`），理由記在 ADR-015 — 不想讓一份 2500 行的舊對話當成剛剛講的話灌進畫面。

從終端機接手一個正在跑的 session 時，這個空白最傷：你不知道它在幹嘛。

## 這一輪查證出來、會改變判斷的事實

**體積沒有想像中大，前提是只送畫得出來的東西。** 本機 313 份 claude transcript，中位數 57KB，最大一份 11MB / 4671 行。那份最大的裡面，真正能變成泡泡的只有 419 則、純文字 204KB；但如果照現行管線原樣轉送所有 renderable record，是 3154 筆、4.97MB。差距 24 倍。讀檔加解析整份只要 38ms — 慢不是問題，量才是。

**「往回讀多少位元組」不能當單位。** 大型 session 裡能變成泡泡的只佔 7–13% 的行數；agent 跑得兇的 session 更極端（本次對話 173 行只有 5 顆泡泡）。往回抓 64KB 有可能一顆泡泡都沒有 — 「載入更多」按了沒反應。要往前掃到湊滿 N 顆為止。

**穩定的訊息身分本來就在檔案裡，只是被丟掉。** claude 的 record 有 `uuid`，omp 有 `id`，兩邊都在 `server/transcript/records.ts:96` 被丟棄。而 `stream_chunk` 的內容欄位是開放的（`z.record(z.unknown())`），多帶一個欄位不是協定變更，不會弄壞手機上已快取的舊版程式。

**鏡射終端機捲軸這條路是死的。** herdr 的 `pane read` 三種模式都只回一個螢幕（44 行 / 2.5KB），沒有可取用的 scrollback。

**有一條語意邊界可用。** transcript 裡有 `compact_boundary` 記錄（omp 是 `compaction`）。11MB 那份最後一個壓縮點之後是 1516 行、約 130 顆泡泡 / 65KB — 那正好等於「agent 自己現在還記得的範圍」。

**localStorage 撐不住而失敗時是靜默的**（`session-persistence.ts:62`），超過約 5MB 就是這個 session 從此不再持久化，畫面上沒有任何徵兆。

## 四條路

### 完整版：穩定訊息身分 + 歷史協定 + 向上捲動載入
你原本要的形狀。三件事綁在一起：訊息 id 改由 transcript 的 record 決定、開始渲染 user 記錄、新增一組歷史請求／回應訊息，client 記住頂端游標，往上捲就再要一頁。

**它同時修掉一個現在就存在的洞**：終端機那邊打的 prompt，手機現在根本看不到（`ws-service.ts:287` 把 user 記錄丟掉了），所有 user 泡泡都是手機自己的本地回音。載入歷史如果不修這個，撈回來的只有 assistant 半邊對話。

**分頁順便解掉體積問題**：一次只送 N 顆泡泡，就算照現行管線原樣轉送也只有那 N 顆的體積，不必為了 204KB 對 5MB 去動 ADR-015「不重塑內容」的承諾。一次全灌的做法沒有這個好處。

**代價**：訊息 id 一旦改由 transcript 決定，手機自己送出的樂觀泡泡就必須跟讀回來的同一句話對帳，否則同一句出現兩次 — 這是立刻要處理的，不是以後再說。持久化的訊息形狀改變，舊的 localStorage 內容要遷移或作廢。產品定義也跟著變：手機從「你在手機上的對話紀錄」變成「這個 session 的鏡子」。

**是否可回頭**：單向門。線上多了一組契約，手機上快取的舊版程式看得到。

### 有界回填：打開時補一段，不做分頁
不加任何協定。附著時把讀回游標往回倒一段，用現有的訊息管道把內容送完就結束。

**代價**：必須以「本機這個 session 目前沒有訊息」當閘門，否則每次重連都再灌一次（現行路徑沒有去重）。還要處理兩個副作用：回填會讓 session 看起來正在跑，回填的訊息時間戳會變成「現在」。而且一次灌完會直接撞上前面說的體積問題。

**是否可回頭**：拿掉就沒了，線上什麼都沒留下。這是「不接受分頁框架」的最小版本。

### 語意邊界：顯示 agent 自己還記得的全部
界線不是一個數字，是上一個壓縮點。往上捲到頂，看到的邊界就是模型記憶的邊界。

**代價**：沒有可調的 N；沒壓縮過的 session 等於「全部」，體積問題原封不動；要重複抓取一樣需要穩定的訊息身分。

### 不做歷史，只把缺口標示清楚
對話頂端一條分隔線：「你從這裡開始看，更早的在終端機」。ADR-015 的決策原封不動，手機維持「當前這一輪的遙控器」，不假裝是對話紀錄。

**是否可回頭**：完全可逆，也是最誠實的下限。

## 有考慮過、但沒放進選項的

**伺服器記憶體環形緩衝，用既有的重連重放機制送出** — 不用新增任何對外契約，client 已經會處理。但它的限制自我否決：伺服器啟動之前的內容永遠不存在。pm2 重啟之後、或昨天開的那個 pane，第一次打開仍然是空的 — 而那正是最常見的情境。

## 選了之後還會遇到的岔路

一旦開始渲染 user 記錄，終端機打的字就會出現在手機上。這不只是技術細節，是產品定義的改變 — 也是唯一能讓歷史安全重複抓取的前提。
